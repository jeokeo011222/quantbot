第四章AI 的手：它能动手，但只能动你允许的那几样东西

4.1为什么不让它自己算收益率

我做过一个小实验，只花了十分钟，但那次之后我改掉了整套设计里的一块砖。 我把一只股票最近 60 个交易日的收盘价粘进对话里，然后问它：“帮我算一下这 60 天的日收益率标准差。” 它给了。数字看起来合理，格式很漂亮，还贴心地把百分比保留了两位小数。 我又换了一个写法问同样的问题：“请用这 60 个数字，按总体标准差（除以 \(n\)）和样本标准差（除以 \(n-1\)）分别算一遍，两个都给我。” 它给了两个数，而且两个数一模一样。 这就是问题所在。它不是“算得不够准”，它是根本没有在算。它在生成一个“看起来像标准差”的数字——这个数字由价格量级、波动直觉和随机性共同决定，而不是由那 60 个数字决定。 而真正让我后背发凉的，不是这个错误本身，是没有人会发现它。 一个模型在报告里写“年化收益 18.7%”，你怎么核对？你得把那几百行价格重新拉出来自己算一遍。也就是说：凡是让模型“心算”出来的数字，它的成本不是错，而是不可核对。
这一章只有一条原则
LLM 负责理解与决策协作，量化引擎负责计算事实。 翻译成人话：模型负责“这件事该不该做、怎么做更稳妥”，机器负责“这个数到底是多少”。两者之间不许互相串岗——模型不许算数，引擎不许做决定。

4.2给新员工开账号

一个新人来上班，第一件事是开系统账号。 你会给他“查库存”的权限，因为他的工作要用；你不会给他“改价格”的权限，因为他用不着——而且一旦他改错了，损失不会停在他自己那一格。 你还得给他工具：一把能算的计算器，和一本能查的资料册。 但你不会让他“用心算”。心算这件事的麻烦在于：它没有痕迹。他算对了，你没看见；他算错了，你也没看见。计算器不一样——它按了什么、算出什么，都是可以被复盘的。 所以给 AI 配工具，其实在回答三个问题：它需要什么能力？哪些能力它不能有？它拿什么去做这些事？ 前两个问题由第 第二章 章和第 第三章 章回答过了，这一章回答第三个。
很多人以为“工具”是为了让模型更强、更快。 不是。工具真正的价值在于把一次计算变成一个可以被检查的对象。 心算的结果只有一个数字，你只能选择信或者不信。计算器按下去之后，会留下“输入是什么、用了哪个公式、输出是什么”。有了这三样，一个数字就从“结论”变成了“证据”。

4.3不给工具，会怎样

三种代价，一种比一种深。 第一，错得没有规律。 心算的错误不是随机噪声，它跟数字的“长相”有关：整数好看的数字容易被写对，带小数的数据容易出错。这意味错误不是均匀分布的，你没法用统计方法把它平均掉。 第二，错得无法传播。 一个模型算出来的收益率，没法成为下一个模块的输入。因为下一个模块拿到的是一段字符串，不是数。它要么放弃使用，要么自己再“理解”一遍——而“理解”这一步又是一次心算。 第三，错得无法追责。 这是最深的一层。如果系统里所有数字都是模型“说”出来的，那么当组合亏钱时，你无法区分三种情况：数据本身错了、计算错了、还是决策错了。三种情况的修复方式完全不同，而你连问题在哪一类都不知道。 所以工具不是“增强”，工具是把计算从语言里搬到代码里。搬过去之后，计算才有痕迹。

4.4从“给模型工具”到“工具契约”

先给一个“差不多对”的模型：工具就是给模型几个可以调用的函数。 这个模型是对的起点，但它在两处会塌。 塌陷一：如果工具返回的是一句话，等于没有工具。 假设有一个工具叫“看看今天的市场”，它返回一段市场评论。那这段评论只能再喂给模型，模型还要再“理解”一次——我们又回到了心算。 要让工具真的有用，它的返回值必须是结构化的：字段名固定、类型固定、能被下一个模块直接当输入用。比如不是“今天市场偏弱”，而是 market_tag="退潮风险"、position_rate=0.06。 塌陷二：如果工具没有“谁能用”的属性，工具越多越危险。 一个工具的集合，同时也是一个人能触达的全部动作。给风控师装上“下单”工具，就等于给了它下单权——不管你提示词里怎么叮嘱。 所以严格的工具不是函数，是一份四件套 + 一张可见性表。
定义 4.1（工具契约）
一个工具由四部分组成：名字、说明、参数结构（JSON Schema 形式的输入声明）、执行方法。此外，每个工具还带一组可见角色——只有列在其中的角色才拿得到这个工具。
一句话解释：前四样决定“这个工具怎么被调用”，第五样决定“谁有资格调用它”。

4.5它在系统里长什么样

4.5.1一个工具的解剖

这段话在说什么：四个函数，四个问题。Name() 答“我叫什么”；Description() 答“我干什么”，而这段说明就是模型选择工具的唯一依据；GetDefinition() 答“我的参数长什么样”，返回的是给 LLM 看的函数声明；Execute() 才是真的动手。 注意最后一行：它返回的是 (interface{}, error)——一个结构化对象，加一个可能存在的错误。没有第三种返回方式。 工具不能说“我觉得大概是”，它只能给出结构，或者报错。 这段话在说什么：这个工具只有两个参数，而且第二个参数只能是两个值之一。参数写死在 JSON Schema 里，模型不能自己发明一个 action="随便试试"。

4.5.2取不到数据，工具会拒绝

这是本章我最喜欢的一段代码。六维判势工具在动手之前，先检查一件事： 这段话在说什么：数据库没挂上，工具不返回“零分”，也不返回“默认中性”，它返回一个错误。工具宁可不干活，也不编数据。 这就是第 第三章 章那两个拒答码在工具层的对应物：DATA_UNAVAILABLE 不是一个礼貌用语，它是链条上每一环都要遵守的行为约定。 拒绝之外的另一半，是它成功时交出来的东西： 这段话在说什么：它交出的不是一句话，而是一张表。六个维度的分数在一栏，冲突数在一栏，仓位系数在一栏，市场标签在一栏。 最要紧的是 sources 这一栏——每个数字“从哪来”和数字一起返回。第 第二十章 章会看到，这一栏里留着的是“这天的数据是用哪个源算的”的原文记录。 还有 note 里那句朴素的话：“所有实时源失败均自动回退并标注，无伪造。” 这是工具对自己行为的公开承诺，而且是写在返回值里的，不是写在文档里的。 而工具算出来的东西是能核对的。比如六维判势的结果落库之后，第二天可以逐条查： 表里的“修正后总分”38.43 与 25.711、“仓位系数”0.10 与 0.062数值取自 market_sixdim_daily 表的 2026-09-10 与 2026-09-11 两条真实记录；同一表的原始总分、冲突数、数据来源字段亦一并入库。核对时间 2026-09-24。3，都是从库里直接读出来的，不是模型写的。工具的价值就在这里：它把“今天市场怎么样”从一句形容词，变成了一行可以复算的记录。

4.5.3一张表决定谁能碰什么

系统在装配团队时，逐个把工具挂到角色身上。当前版本一共 25 个工具注册入口，注册调用的代码集中在 internal/brainhost/team_tools.go 第 338--452 行区间该 25 个注册入口见系统事实清单第 5 节“工具清单”，核对时间 2026-09-24。4。 这些工具的真身分布在 internal/tools/ 下的 22 个源码文件里，包括 sixdim_tool.go、daily_strategy_tool.go、factor_review_tool.go、order_book_tool.go、backtest_gap_tools.go、cninfo_tools.go 等文件清单见系统事实清单第 5 节“工具源码文件”，核对时间 2026-09-24。5。 对外的工具名与可用角色，如表 4.2。这张表建议你抄一遍——它是整本书里出现频率最高的一张表。 这张表里藏着一个很容易被忽略的不对称： run_backtest 只有 QUANT 能用。回测是“研究”，研究的结果必须经过风控和 CIO 才能变成动作——所以把它锁在链条的第二环上。 market_sixdim_detect 有四个角色能用。“今天市场好不好”是共享上下文，不是谁的私产：规划师要靠它定配置、量化要靠它排候选、风控要靠它设限额、CIO 要靠它缩仓位。 get_cninfo_info 是唯一覆盖四个角色（含 PLANNER）的“外部信息”工具。它查的是巨潮的公司公告——这是外部世界的事实，不属于任何岗位的私有财产。

4.5.4每个角色手里有几把工具

看最后一行和第一行，把它们对起来读： TRADER 独占下单工具，却没有选股工具；CIO 工具最多，却拿不到下单工具。 第 第二章 章那条“只有 Trader 能执行订单、只有 CIO 能选择股票”的硬约束，在这里第二次出现——这一次它是用工具清单写出来的。 权限表是一道门，工具可见性是第二道门。两道门用不同的方式表达同一件事，谁改错了一道，另一道还拦得住。

4.5.5运行时还有一次校验

工具在装配时按角色挂载，只解决了“它有没有”的问题。系统里还有一个工具注册表（internal/port/agent.go 的 ToolRegistry），每个工具的元数据里除了名字、分类、风险等级，还有一栏 Roles：这个工具可以被哪些角色调用。 中央注册表是这样建起来的： 每个工具在注册时，都必须当场写清它属于哪个分类、风险等级多高、允许哪些角色调用。三条最有代表性的注册声明长这样： 三行声明里，三件事同时被写死：run_backtest 只给 QUANT，风险等级 medium；place_trade 只给 TRADER，风险等级 high；market_sixdim_detect 给 CIO、PLANNER、RISK、QUANT 四个角色，风险等级 low。 注意 place_trade 挂的是 high，而六维判势挂的是 low。在这份注册表里，标到最高风险等级的那一个，正是唯一能下单的那一个。能力越大的工具，它的元数据越扎眼——这不是为了好看，是为了让“谁在什么时候能调用什么”这件事变成可以逐条翻出来的记录，而不是藏在某段代码逻辑里。 注册完之后，这份注册表被逐个注入每个智能体（第 329--334 行），由智能体在运行时调用工具前再校验一次角色。装配是静态的，校验是动态的——同一条边界，在两个时刻各自确认一次。 我特意保留了这张表的“多余”：装配时已经按角色挂过工具了，为什么还要在运行时再查一遍？因为装配只发生在启动那一刻，而运行时校验发生在每一次调用。如果哪天有人加了一条新代码路径，绕过了装配直接调工具，第一道门不会拦——第二道门会。 要提醒一句：这份注册表与前面那 25 个注册入口不是同一份清单——前者按工具登记“谁能用”，后者按角色登记“我有什么”。两份清单各自列举，也各自可以被单独核对。

4.6常见误解与纠偏

“接上 Function Calling 就解决了”——这句话听起来像技术方案，其实是个情绪安慰。 工具能不能解决问题，取决于三件非常具体的事： 第一，返回值是不是结构化的。 返回一段自然语言，等于没返回。第 第二章 章那张权限表能成立，是因为“允许/拒绝”是两个布尔值；如果它是“原则上可以”这种文本，这张表立刻失效。 第二，取不到数据时它返回什么。 是报错，还是返回一个“默认中性 50 分”？后者看起来更“稳定”，代价是你会拿一堆假数据去做真决策。 第三，谁能调用它。 没有这一条，Function Calling 只是把模型的手变长了，没有把它关进笼子里。
我一度以为工具越多越好：给 CIO 挂 24 个工具，它应该更强。 事实是：工具越多，选错工具的概率越大。每个工具都有一段说明，模型要在这些说明之间做选择。工具的功能越重叠、名字越接近，它越容易挑错——而挑错工具往往不会报错，只会拿回一份“看起来相关”的数据。 所以工具数量的增长，必须伴随两件事：每个工具有明确的“不重叠”的说明，以及每个工具有明确的可见角色。 表 4.3 里那五个数字之所以有意义，不是因为它们大，而是因为它们不相等——不相等，说明有人被故意挡住了。
工具说明不是文档，它是提示词的一部分。 模型看不到工具的内部实现，它只看到名字和一段描述。所以“这个工具被正确使用”这件事，一半的责任在写工具的人身上，而不是在模型身上。 反过来看 market_sixdim_detect 的说明：它把六个维度的名字、“输出各维度得分、冲突修正后总分、建议仓位系数 position_rate 与市场标签”、以及最要紧的那句“策略信号仓位 = 原始信号仓位 × position_rate”，全部写进了描述里。 这不是啰嗦。这是在把“该怎么用我”提前告诉调用者。工具描述写得含糊，模型就只能猜；它一猜，你就得去核对它猜的对不对——于是你又回到了这一章开头那个“没有人会发现”的处境。
