附录 J系统标识符索引

关于“查”，本书前面已经有两份附录了。附录 G 的术语表回答这个词是什么意思，附录 H 的事故索引回答这个毛病怎么修。这一份回答第三个、也是在真实使用里被问得最多的问题：这个东西，书里还有哪些地方讲过？

J.1怎么用这份索引

三条约定，读之前先看一眼：
  1. 出处写的是章节号，不是页码。 数字就是章号（14 = 第 14 章），大写字母是附录编号（F = 附录 F）。之所以不写页码：页码是排版的产物，本书改一次行距、加一张图，后面几百页的页码全体平移，索引就全错了；章节号是源文件本身的属性，不会漂移。代价是定位粒度粗一级，收益是这份索引不需要随每次重排而重编。
  2. 索引里的键，是系统里的真实标识符。 等宽字体写出来的每一个名字，都可以直接复制到源码目录里去检索。索引不对它们做任何改写、转写或翻译。
  3. 索引收了什么、没收录什么，下面第二节逐条说明。
举三个真实例子，说明这份索引在什么时候有用：
  • 你在第 19 章读到字段 position_rate，想知道它在别处还出现过没有。查索引：14, 19, 28, G——它第一次被定义在第 14 章，第 28 章讲组合时又用了一次，附录 G 的术语表里有一条。
  • 你想知道系统那张六维判势日表 market_sixdim_daily 到底牵扯了多少地方。查索引：16 个出处（第 4、5、6、7、10、11、14、19、20、21、22、28、33 章，以及附录 A、B、E）。它是全书被引用最广的一张表——这本身就说明六维判势在系统里的位置。
  • 你在系统里看到一个函数 select_next_day_strategy，想知道本书讲了没有。查索引：1, 4, 16, 30, 32。第 1 章是总览提了一句，第 4 章讲智能体时正式介绍，第 16 章讲策略生成、第 30 章讲实操、第 32 章讲它出错时怎么办。

J.2收录范围与规模

类别条目数收录范围与不收录的理由

源码文件与包152正文脚注与「真实出处」小节里指过的文件路径。路径末尾没有文件名的是包目录。
合计324去重后的标识符总数，其中 108 个出现在 2 个及以上的章节或附录里。

统计口径：对 chapters/ 与 appendices/ 下全部 .tex 源文件做文本抽取，按标识符去重。数字随正文增删而变，可用 python gen_identifier_index.py --check 当场复核；本节数字与下面索引的内容出自同一次抽取，不会互相矛盾。

有三件事必须说清楚，否则这份索引会给人一个错误的印象。 第一，它不收录 code 宏里的内容。 全书 code 宏用了 2 278 次、去重后有 1 289 个不同的字符串，但其中绝大多数是代码片段而不是标识符——赋值语句、切片表达式、格式化字符串都算在内。把代码片段做成索引没有意义，读者不会去查一条语句，也查不到。所以索引只收那四个「给东西起名字」的宏：工具名宏 tool、表名宏 dbtab、字段名宏 field、路径宏 sysfile。你如果确定要找一个函数名（比如 OutputGuard.ValidateOutput），而它恰好只出现在 code 宏里，那它不在本索引中，请改用 PDF 阅读器的全文搜索。 第二，它是机器生成的，不是手写的。 索引里的每一条都来自对源文件的文本抽取，没有任何人工增删。生成器还会做一次双向核对：源文件里出现的标识符必须在索引里，索引里的标识符也必须在源文件里，两边条数必须相等。这个核对每次生成都跑，不通过就写出告警。换句话说，你在这份索引里找不到的，正文里确实没有。 第三，它的构建过程真的抓到过东西。 生成器最初的设计里有一条「同一标识符被两种宏引用即告警」的规则——同一个名字，不可能既是一个源码文件又是一个数据表。这条规则当场抓出了两处真实的宏用错：第 11 章把表名 FactorQuality 误写成源码文件宏，第 20 章把表名 order_book_daily 误写成字段宏。两处都已修正。这类错误不影响编译、不影响版面、也不会进任何日志，只有把全书的名字放到一起数才看得见。
