B.2SQLite：58 张业务表

下面这张表按用途分组列出全部 58 张表，并给出行数。行数一栏值得你多看两眼——绝大多数字段位是 0，因为这套系统在本机只跑过很短一段时间，很多功能还没有真实数据流过。这不是缺陷，是「还没有发生过」；本书凡引用数字，只引有行数的那几张。

「组」为本书归纳，代码里没有这个字段。行数一栏只列该组内非零的那几张表，按「权限 / 活动 / 成员」等顺序对应表名里最先出现的那几项；组内其余表均为 0 行。统计口径：逐表 select count(*)。

只读查询 database/quantpilot.db 的 sqlite_master 与逐表 count(*)；时间 2026-09-24。全库共 58 张业务表（另有 SQLite 内部的 sqlite_sequence）。系统事实清单早期记为 39 张，本书以运行库实测为准。

不等于。表建出来了、写入路径也在，只是本机还没跑过触发它的那条流程。判断一个功能是否可用，要看三条：表存在、写入代码存在、以及有没有真实行数。只有前两条时，功能是「已实现、未验证」；第三条也有了，才叫「跑通过」。 本书对这三种状态分得很清：正文里凡出现数字，都能在下表「有行数」的那几张里找到；找不到就写「数据缺失」，绝不用空表反推一个数出来。

B.3DuckDB：行情与基本面

四条必须记住的口径： 第一，stock.ohlc 覆盖 2021-08-02 至 2026-09-24，去重后 9,584 个 symbol；末两日是残档（仅几十个 symbol），做统计必须挑「最近完整交易日」——16 本书用的是 2026-09-23。 第二，stock.stock_basic 里混着 ETF / 基金（如 sz167301、sz200570），它们的 name 为 NULL。做「个股」统计时必须先过滤，否则分母被撑大。 第三，market_sixdim_daily 是本库最有价值的一手素材，但只有 5 行（2026-08-31、09-02、09-09、09-10、09-11）。第 19、20、21 章把它逐条手算过；多一行都没有。 第四，本库是挂载库。建表与数据都在 main schema 下，日常代码里写 stock.ohlc 是命名空间习惯；你在 SQL 里写 ohlc 同样能查到。17 本书不对「order_book_daily 的盘口统计」做任何引用——该表 0 行。

B.4「以数据库为准」的三条口径

界面上的数字、日志里的数字、数据库里的数字，三者不一致时，本书一律按这个顺序裁决：
  1. 数据库是唯一事实来源。界面是投影，日志是过程记录；两者与库冲突时，以库为准。第 29 章「差了三块五」讲的就是这条。
  2. 派生数字必须能当场复算。凡是「按公式算出来的」数（总分、仓位系数、盈亏、胜率），本书都在正文里给出公式与输入，读者可自己算一遍对账。
  3. 缺数就留白。库里没有的记录，标注「数据缺失」并停笔；不插值、不估计、不用空表反推。
  • SQLite 表清单与行数：database/quantpilot.db 的 sqlite_master 加逐表 count(*)，2026-09-24
  • SQLite 建表来源：internal/data/sqlite.go 的 AutoMigrate（47 张）、internal/agentworkflow/models.go 的 MigrateAgentWorkflow（8 张），其余由各包内建表
  • DuckDB 表与行数：data/stock.duckdb，2026-09-24；结构对照系统事实清单第 13.2 节
  • 两库分工：系统事实清单第 13 节
动手试一试

  2. 找非空表。对每张表跑 count(*)，你会发现只有十来张不是 0 行。把非空的挑出来，就是这本书「敢引用」的全部范围。
