第三十三章出问题怎么办：日志、黑匣子与常见故障

33.1一次日志里什么都没写的闪退

系统稳定跑了几天之后，出了第一个真正的怪事。 下午两点四十分，我正在看持仓页。窗口“啪”地消失了。托盘图标也没了。进程干干净净地退出。 我第一件事是打开日志目录，找那条最新生成的 log/quantbot_<时间戳>.log。翻到末尾——记录停在两分钟前的一句“刷新持仓行情”，后面什么都没有。 没有异常、没有堆栈、没有“exit”。 我又去看 Windows 事件查看器，想找一条应用程序错误。空的。 那是整件事最让人不安的地方：一个程序死了，而它没有留下任何关于自己为什么死的记录。这不像“报错了”，更像“被抹掉了”。 后来我们把原因找出来了。它不是玄学，是一段非常具体的代码——而且它精确地展示了本章要讲的三件事：为什么致命的错误会“静默消失”、该怎么给它专门造一条通道、以及拿到转储之后怎么复原现场。

33.2黑匣子的读法

一架飞机失事后，调查组的第一步不是猜“可能哪里坏了”，而是去找黑匣子。 找到之后他们做什么？不是从头读一遍全部录音。他们做三件事： 第一，确认记录装置本身是好的（别读一份损坏的磁带）； 第二，按时间轴定位到最后一个异常点； 第三，往前后各展开一点，看“异常之前发生了什么正常的操作”。 这套读法的前提只有一个：那个装置必须存在，而且它必须能把最后那几秒写下来。 程序排障是同一件事。所以第一个问题永远不是“哪儿错了”，而是——它把错误写在哪里了？

33.3为什么致命错误会“静默消失”

先讲清楚本章开头那个现象。它是一个纯粹的语言运行时机制问题，没有任何神秘色彩。 Go 语言里有两类“崩溃”：
  • 普通 panic：可以用 recover 接住，也可以被日志框架记录；
  • 运行时致命错误（fatal error：栈溢出、内存越界导致的段错误等）：它不会被 recover 捕获，直接终止进程。
关键在于第二类写到哪去了。它输出到标准错误流（os.Stderr）。而一个图形界面程序没有控制台窗口——标准错误没有人接，写进去就消失了。 于是就有了那个现象：进程死了，日志干净，事件查看器干净。
命题 33.1（无痕故障的概率下界）
设系统在单位时间内发生致命错误的概率为 \(p>0\)，且条件独立地，任一错误被写进某个可观测通道的概率为 \(q\in[0,1]\)。则
  1. “错误发生且无痕迹”的概率为
    \[\Prob(\text{无痕故障})=p\,(1-q); \tag{33.1}\]
  2. 当 \(q=0\)（没有任何通道接收致命错误）时，该概率恰为 \(p\)——所有崩溃都无痕；
  3. 系统连续运行 \(T\) 个时间单位，至少发生一次无痕故障的概率为
    \[1-\bigl[1-p(1-q)\bigr]^{T}\;\xrightarrow[\;T\to\infty\;]{}\;1 . \tag{33.2}\]
这个命题在说什么：它把“概率极小的崩溃在 7×24 运行的系统里是必然事件”这句话变成了一个极限。第 (ii) 条更狠——\(q=0\) 时，“发生”就等于“无痕”，你没有任何可观测性，不是可观测性变差了。
证明■
(i) 设事件 \(E=\)“发生致命错误”，\(\Prob(E)=p\)；事件 \(R=\)“被记录”，\(\Prob(R\mid E)=q\)。则
\[\Prob(\text{无痕})=\Prob(E\cap R^c)=\Prob(E)\Prob(R^c\mid E)=p(1-q).\]
(ii) 代入 \(q=0\)：\(p(1-0)=p\)。 (iii) 设 \(T\) 个单位时间彼此独立（故障发生的独立性假设），每个单位时间内“无痕”的概率为 \(\rho:=p(1-q)\)。\(T\) 个单位全部没有无痕故障的概率为 \((1-\rho)^T\)，故至少一次的概率为 \(1-(1-\rho)^T\)。当 \(\rho>0\) 时 \((1-\rho)^T\to0\)，故其趋于 \(1\)。\(\blacksquare\)
这个命题给出的行动项非常明确：你无法把 \(p\) 降到 0（那是硬件的噪声底），但你可以把 \(q\) 提到 1。而把 \(q\) 提到 1，只需要一行代码——把致命错误的输出重定向到一个文件： 这段话在说什么：它没有阻止崩溃，也没有让崩溃变少。它只做了一件事——把原来掉在地上的东西，接进了一个桶里。这一行是本章里性价比最高的一行代码。

33.4那个段错误的完整故事

现在讲本章开头那次闪退的真正原因。它在事实清单里是第 #1 条，也是全书我认为最值得完整复述的一次修复。
真实事故 #1（完整形态）
症状：程序运行中突然闪退，日志干净，Windows 事件日志无记录。
根因：决策完成后调用 agent.dll.Release() 卸载了这个 DLL；而它（一个 c-shared 的 Go DLL）内部还有后台 goroutine 在运行。卸载导致这些线程继续执行“已经被释放的内存空间里的代码”，触发 ACCESS_VIOLATION (0xC0000005)。
修复：不再卸载 DLL，让它驻留整个进程生命周期。
为什么这个错误“无痕”？因为它是一个访问违例——它在 Go 运行时的层面是致命错误，按命题 33.1(ii)，\(q=0\)，所有痕迹都被丢掉了。 为什么它“偶发”？因为它需要两个条件同时成立：卸载发生了，并且那个后台线程恰好还在跑。第二个条件带时序，所以它有时崩、有时不崩——这类“偶发”最容易被误判成玄学。
命题 33.2（卸载后使用是这一类崩溃的充分条件）
设模块 \(M\)（DLL）被映射到地址区间 \(\mathcal A\)，并在其内部创建了线程 \(\tau\)。
  1. 若 \(\tau\) 仍在运行，而 \(M\) 被卸载，则 \(\mathcal A\) 被解除映射（随后可能被分配给其它模块）；此时 \(\tau\) 的指令指针一旦落回 \(\mathcal A\) 范围，取指将访问不再是 \(\tau\) 所属代码的页面，产生访问违例。
  2. 若不卸载 \(M\)，则 \(\mathcal A\) 在整个进程生命周期内保持映射，\(\tau\) 无论何时被调度，其指令指针始终指向有效且正确的代码，上述崩溃不可能发生。
这个命题在说什么：它把“为什么不能卸载”和“为什么不再卸载就好了”写成了一对互补的陈述。(i) 是崩溃的成因链；(ii) 说明修复不是“降低概率”，而是移除了发生条件。
证明■
(i) 卸载 \(M\) 意味着操作系统把 \(\mathcal A\) 从进程的地址空间中移除，并回收这些物理页。此后 \(\tau\) 若被调度器选中，CPU 要用 \(\tau\) 保存的指令指针 \(ip\in\mathcal A\) 去取指令。由于 \(ip\) 落在未映射区域（或已映射给别的数据），该次取指不可能是 \(M\) 原有的正确指令：要么触发缺页异常且无法被合法处理，要么取到已经变成别的内容的字节。二者都会让 \(\tau\) 进入一个非法的执行状态，表现为访问违例（0xC0000005）。这里的关键点是：\(ip\) 落在 \(\mathcal A\) 内是充分条件——不需要知道那块内存被谁占了。 (ii) 若不卸载，则 \(\mathcal A\) 与 \(M\) 的代码、数据在整个进程生命周期内一一对应且保持不变。\(\tau\) 的指令指针无论何时取指，读到的都是 \(M\) 被编译时的正确指令；访存地址也都落在仍然有效的 \(M\) 的段内。故 (i) 中描述的条件无法成立，该崩溃不发生。\(\blacksquare\)
这次修复之后，同一个流程再没有出现过同类闪退。它留下的教训可以写成一则通用经验：
一条通用经验：谁创建的线程，谁负责它的生命周期
卸载一个模块的前提是确认它创建的所有执行流都已结束。做不到这一点时，正确做法是不卸载——让它在进程里待着，代价是一点内存，收益是消除一整类不可观测的崩溃。

33.5故障的三种类型，和三种查法

修完那一次之后，我给自己立了一条规矩：不要一上来就猜原因，先分类。因为三类故障的查法是完全不同的，混着查只会浪费时间。 三类里最容易误判的是第二类。它表现得很像“功能坏了”，于是人的第一反应是“先让它能跑”。但第 第二十章 章已经讲过：“能跑但数据是假的”比“跑不起来”危险得多。所以数据类故障的正确反应是停下来，然后去看它为什么缺。

33.6现场清单：出事了先去哪几个地方

下面这张表是我实际会按顺序查的清单。它的顺序就是“从最近发生的、到最底层的”。

33.6.1常见故障速查

“它有时候崩有时候不崩，说不清。” 这句话不是结论，是还没分类。判断方法很简单：看它有没有规律地跟某个动作绑定。
  • 如果它总在同一句操作之后崩，那是配置类或数据类——必现，可复现，读错误信息就能定位；
  • 如果它偶发、无日志、直接消失，那几乎一定是并发/内存类——这时唯一有用的东西是崩溃转储，而不是重试。
“偶发”是最容易被当作借口的三个字。事故 #1 就是标准的偶发：它需要“卸载”与“后台线程正在跑”同时发生。当你把这两个条件写出来，它就不再偶发了——它变成了一个有明确触发条件的确定性事件，只是触发时机不确定。 这本书里另一个同类例子是事故 #3（托盘右键菜单弹不出来）。它的根因是：Wails 的启动流程常跑在非主线程上，而 Windows 的窗口消息只发给“创建那个窗口的线程”。所以托盘窗口必须在一条自己锁定的线程上创建，并跑自己的消息泵——否则左键右键都永远无人响应。它同样表现为“有时好有时坏”，同样不是玄学。
这是全书反复出现的一条，放在最后一章是因为它最容易被“排障”这个场景重新触发。 排障时人会有一种强烈的冲动：只要能让流程跑完，就先跑完。于是行情库缺了就找另一张表、API Key 无效就先跳过 AI、判势缺一个维度就随手给个 60。 第 第二十章 章已经给出结论：代理变量可以用，但必须当场标注；连代理都没有时，正确的动作是留空，而不是填一个看起来合理的数。 因为在排障这个场景里，你做的每一个“临时”决定，都可能在系统里活很久——尤其是当它让流程看起来正常了之后，就再也没有人会回去检查它。 系统把这条写成了硬约束：关键组件失败必须弹窗报错，严禁降级、严禁使用虚假数据。那个“仍然继续”的按钮是给你知情之后用的，不是给你绕过红灯用的。

33.7最后一件事：回到第 1 章那个问题

第一章开头是这样一个问题：一个人，怎么同时当研究员、风控和操盘手？ 当时的回答是：不要找一个人，开一家五个人的小公司。 现在全书读完了，我们可以把那个答案补完整。那家小公司之所以成立，不是因为它雇了五个很聪明的 AI。而是因为这六样东西被一条一条写进了代码：
  • 分工——五个角色，每个角色有明确的任务类型（第 第一章、第三章 章）；
  • 权限——谁能下单、谁能选股、谁有否决权，写在权限表里，不是写在提示词里（第 第二章 章）；
  • 契约——派活的标准格式；不给它“编”的出口，它就编不出来（第 第三章 章）；
  • 证据——决策发生的同一时刻同步落证据，而不是事后补一段解释（第 第十章 章）；
  • 容错——只降不升的仓位、失败即拒的启动、AI 失联时的规则回退（第 第七章、第九章、第二十四章 章）；
  • 诚实——数据不可用就报错，代理变量必标注，样本不够就说“无法判定”（贯穿全书）。
这六样，没有一样是“让模型更聪明”能替代的。它们的共同点是：都可以被写下来、被检查、被反驳。 而这恰好也是本书想留下的东西。你读完之后不必拥有这套系统——你可能用别的软件、别的语言、甚至完全手工。但你手上应该多了一套问题，用来问任何一套自称“AI 帮你投资”的东西：
临走时带走的六个问题
  1. 它会不会拒绝？（有没有权限边界，还是谁都能下单）
  2. 它会不会说“我不知道”？（有没有 DATA_UNAVAILABLE 这样的出口）
  3. 它算出来的数，我能自己复算一遍吗？（因子、分数、仓位，有没有公式）
  4. 它的回测有没有偷看未来？（成交价口径、切分方式、成本项）
  5. 它亏了之后，能查到当时看到了什么吗？（证据链、审计日志）
  6. 它错了之后，明天会不一样吗？（复盘有没有产出参数变化）
我在第一章写过一个身份转换：从“操盘的人”，变成“开公司的人”。 全书读完之后，我把它再补一句。你依然是那个开公司的人，但现在你手里多了一样东西——你不再需要相信它。你可以查它、算它、验它、关它。 这就是这套系统最后想给你的一种感觉：不是“我把钱交给了一个很聪明的东西”，而是“我搭了一台我说得清楚的机器，并且它不敢骗我”。

  2. 检查 log/crash_dump.txt 是否存在。若存在，读第一条；若不存在，说明本机还没发生过致命崩溃——但请确认那条重定向代码在运行（看 main.go）。
  3. 去设置页的「数据维护」，看行情库最新更新到哪个交易日。若不是上一交易日，就按第 第二十五章 章的顺序补一次。
  4. 打开审计日志页，随便找一条决策，看看它能不能回答这个问题：“当时它看到了什么？”
  5. 最后做一次“演习式提问”：假设现在选股页返回 \(0\) 只结果。请你按本章的清单，列出你会依次检查的三个地方，并说明每一个能排除哪种可能。
